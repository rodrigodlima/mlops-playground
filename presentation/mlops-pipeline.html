Definition

MLOps is DevOps for models.

A pipeline that turns raw data into a production model, keeps it observable, and lets you roll it back. Five stages, all reproducible: data → train → register → serve → monitor.

  • Reproducible — same code + same data + same seed = same model. Versioned everywhere.
  • Automated — retrain on a schedule or a trigger (data drift, new label batch, calendar).
  • Observable — you know when accuracy quietly tanks at 3am, before the user does.
01What
The five stages
Intro What How Trade-offs Demo vs.
The pipeline

Five stages, end-to-end.

01DataIngest, validate, version. Feature store or DVC.
02TrainRun jobs. Track params, metrics, artifacts.
03RegisterPromote artifact: Staging → Production.
04ServeREST/gRPC. Batch or online. Autoscale.
05MonitorDrift, latency, accuracy. Page on regression.

Each stage emits artifacts. Each artifact is signed, versioned, and reproducible from upstream inputs — same contract you already use for container images.

02How
Data layer
Intro What How Trade-offs Demo vs.
Data + orchestration

Feed the beast.

  • Feature store (Feast, Tecton) — single source of truth for features. Same code path training and serving — kills training/serving skew.
  • Data versioning (DVC, LakeFS) — git-like history for datasets. Hash + pointer, not the bytes in git.
  • Orchestrator (Airflow, Prefect, Argo) — DAG of training jobs. Same role as Jenkins for code, but ML-aware.
  • Triggers — schedule, data drift threshold, manual approval. Treat retraining as a deploy event.
  • Validation gates (Great Expectations) — fail the pipeline if input schema breaks. Cheaper to fail at ingest than at inference.
02How
Train + register
Intro What How Trade-offs Demo vs.
Tracking + registry

Every run is an artifact.

  • Experiment tracker — every fit() logs params, metrics, code SHA, dataset hash, environment. Reproducible build, but for a model.
  • Model registry — promotion lanes (None → Staging → Production → Archived). Same shape as your container registry, with semver-style aliases.
  • Lineage — registry row points back to the run, the run points back to the dataset version. Trace a prod prediction back to its training data in 30 seconds.
  • Approval gates — flip the stage label via API/UI. Wrap it in your existing change-management process.
  • Signing & SBOM — sign model artifacts; track Python deps. Yes, supply-chain attacks target ML too.
02How
Serve + observe
Intro What How Trade-offs Demo vs.
Serving + observability

Ship it. Watch it.

  • Online serving — FastAPI for prototypes; KServe / Seldon / BentoML for k8s-native autoscaling, canary, traffic split.
  • Batch serving — Spark / Ray / cron writing predictions to a warehouse. Cheaper, no SLA on tail latency.
  • Drift monitoring (Evidently, WhyLogs) — compare input distribution today vs training day. Page when KS-test or PSI crosses threshold.
  • Quality monitoring — once labels arrive, recompute accuracy/AUC on production data. The thing that actually matters.
  • Infra metrics — Prometheus for QPS, p99 latency, OOM. Same dashboards you already have.
03Trade-offs
Architecture choices
Intro What How Trade-offs Demo vs.
Build vs buy

Monolithic platform vs composable stack.

Monolith (SageMaker / Vertex)

  • One vendor, one bill, one auth surface.
  • Day-1 productive: managed everything.
  • Strong defaults — drift, monitoring, registry all wired.
  • SOC2/HIPAA boundaries already drawn.

Trade-off

  • Lock-in: SDK + storage + identity all proprietary.
  • Egress is painful; multi-cloud is harder.
  • You inherit the vendor's opinions even when they hurt.
  • Premium-priced compute compared to raw EC2/GKE.

Composable (MLflow + KServe + Evidently)

  • OSS — fork, audit, run anywhere (incl. on-prem).
  • Best-of-breed per layer; swap without rewriting.
  • Cheaper at scale; you pay for compute, not the brand.
  • Skills transfer between jobs.

Trade-off

  • You own the seams. Glue code, upgrades, on-call.
  • Auth/RBAC across 4 systems is not free.
  • Day-1 setup is weeks, not hours.
  • Drift detection is opt-in — easy to skip.
03Trade-offs
Operational choices
Intro What How Trade-offs Demo vs.
Day-2 decisions

How you actually run it.

Decision Pick when… Watch out for…
Online vs batch serving Online: low-latency, per-request. Batch: nightly predictions to a table. Online costs more & needs on-call. Batch goes stale between runs.
GitOps for models You want PR review, audit, rollback by commit revert. Promotion = merge. Model binaries don't belong in git. Store hashes, not weights.
Imperative deploys Small team, fast iteration, no compliance pressure. "Who deployed which model where?" becomes unanswerable.
Drift detection High-impact predictions (finance, health), or non-stationary data. Cost (storage + compute). Alert fatigue if threshold too tight.
Auto-retraining Data shifts faster than humans can react (e.g., recsys, fraud). A bad retrain ships a bad model. Always gate on eval set.

Live demo · MlFlowStarter

MLflow in 30 lines.

Goal: prove the tracker + UI loop works locally, then point at it from a notebook. Three steps:

  • 1. Start tracking server — mlflow ui --port 5001. SQLite backend, file artifacts.
  • 2. Point notebook at it — mlflow.set_tracking_uri(...) + set_experiment(...).
  • 3. Wrap any code in a run — with mlflow.start_run(): and log metrics. UI updates live.

Step 1 · server

Step 1 — tracking server

Start the tracker locally.

terminal · MlFlowStarter/
$ cd MlFlowStarter
$ pip install -r requirements.txt   # mlflow, scikit-learn, pandas, numpy
$ mlflow ui --port 5001
[INFO] Listening at: http://127.0.0.1:5001
[INFO] Backend: sqlite:///mlflow.db  Artifacts: ./mlruns

UI + REST API on the same port. :5001 instead of :5000 to dodge macOS AirPlay. Backend store + artifact store are two different things — for prod, point at Postgres + S3.

04Demo
Step 2 · log run
Intro What How Trade-offs Demo vs.
Step 2 — log a run

Point the notebook at the tracker.

python · get-started.ipynb
import mlflow

mlflow.set_tracking_uri("http://127.0.0.1:5001")
mlflow.set_experiment("Check localhost connection")

with mlflow.start_run():
    mlflow.log_metric("test", 1)
    mlflow.log_metric("Name", 2)

Same shape for a 30-line toy and a 30M-param model: experiment → run → log. Add log_param, log_artifact, log_model and you're production-shaped.
